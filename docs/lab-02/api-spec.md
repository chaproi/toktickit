# Lab 2 REST API Specification

## 1. Purpose

This document defines the REST API contract for the TokTickIT Requester Ticketing MVP. It specifies endpoints, headers, parameters, request and response bodies, HTTP statuses, validation behavior, ownership protection, attachment handling, and safe errors.

All routes use the `/api` prefix.

## 2. Common Conventions

### 2.1 Content Types

* JSON requests shall use `Content-Type: application/json`.
* JSON responses shall use `Content-Type: application/json`.
* Attachment uploads shall use `multipart/form-data`.
* Attachment content responses shall use the stored safe MIME type.
* JSON property names shall use `camelCase`.

### 2.2 Date and Time

* API timestamps shall use ISO 8601 UTC strings.
* Example: `2026-09-03T14:30:00.000Z`.
* The client may convert timestamps into a readable local date and time.
* Ticket creation time shall be generated by the backend.

### 2.3 Identifiers

* Database resource identifiers shall be positive integers.
* `ticketNumber` shall use the format `TKT-YYYY-NNNNN`.
* `clientSubmissionId` shall be a valid UUID generated by the client.
* Clients shall treat identifiers as opaque values and shall not calculate the next identifier.

### 2.4 Requester Context Header

Endpoints that access Requester-owned Tickets or Attachments require:

```http
X-Development-Requester-Id: 1
```

Rules:

* The value must identify an active Development Requester.
* A missing, malformed, inactive, or unknown Requester identifier returns `400 Bad Request`.
* The header is a development-only testing mechanism.
* It must not be described or implemented as production authentication.
* A Requester attempting to access another Requester’s resource receives the same `404 Not Found` response as a missing resource.

### 2.5 Trimming and Unknown Fields

* User-entered strings shall be trimmed before validation and storage.
* Whitespace-only required values shall be treated as empty.
* Unknown request-body fields shall be rejected with `400 Bad Request` and the `VALIDATION_ERROR` code.
* This behavior shall be covered by planned test `API-03`.
* The API shall never trust client-generated Ticket Numbers, Ticket dates, status, ownership, attachment paths, or storage identifiers.

## 3. Common Error Format

All JSON API errors shall use:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Please correct the highlighted fields.",
    "fields": {
      "summary": "Summary must contain 5 to 150 characters."
    }
  }
}
```

### 3.1 Error Properties

| Property          | Required | Description                                              |
| ----------------- | -------: | -------------------------------------------------------- |
| `error.code`      |      Yes | Stable machine-readable error code                       |
| `error.message`   |      Yes | Safe user-readable message                               |
| `error.fields`    |       No | Field-specific validation messages                       |
| `error.requestId` |       No | Non-sensitive identifier for server-side log correlation |

### 3.2 Safe Error Rules

Error responses must not expose:

* Stack traces
* SQL or Prisma error details
* Database connection strings
* SeaweedFS addresses or internal responses
* Local file-system paths
* Internal source-code paths
* Secrets, tokens, or environment variables
* Information confirming the existence of another Requester’s resource

Unexpected failures shall return a general safe message:

```json
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "Something went wrong. Please try again."
  }
}
```

## 4. HTTP Status Summary

|                       Status | Use                                                                            |
| ---------------------------: | ------------------------------------------------------------------------------ |
|                     `200 OK` | Successful retrieval, repeated idempotent creation, or successful soft removal |
|                `201 Created` | New Ticket or Attachment created                                               |
|            `400 Bad Request` | Missing Requester header, malformed parameters, or validation failure          |
|              `404 Not Found` | Resource missing or not owned by the selected Requester                        |
|               `409 Conflict` | Active attachment limit reached or conflicting operation                       |
|                   `410 Gone` | Removed owned attachment content requested                                     |
|      `413 Content Too Large` | Uploaded file exceeds 5 MB                                                    |
| `415 Unsupported Media Type` | Uploaded file type is not allowed                                              |
|  `500 Internal Server Error` | Unexpected server failure with safe message                                    |
|    `503 Service Unavailable` | Required database or attachment-storage service unavailable                    |

## 6. Ticket Endpoints

### 6.1 Create Ticket

```http
POST /api/tickets
X-Development-Requester-Id: 1
Content-Type: application/json
```

Request body:

```json
{
  "clientSubmissionId": "5b7f6b32-e929-4ac8-9c95-079956888f2f",
  "categoryId": 1,
  "relatedSystemId": 2,
  "requestedPriority": "MEDIUM",
  "summary": "Laptop battery drains quickly",
  "description": "The battery decreases from full to empty in approximately one hour."
}
```

The Requester identifier must come from `X-Development-Requester-Id`. A client-supplied ownership field in the body must not override the header.

#### Validation Rules

| Field                | Rules                                                          |
| -------------------- | -------------------------------------------------------------- |
| `clientSubmissionId` | Required valid UUID                                            |
| `categoryId`         | Required positive integer identifying an active Category       |
| `relatedSystemId`    | Required positive integer identifying an active Related System |
| `requestedPriority`  | Required; `LOW`, `MEDIUM`, `HIGH`, or `URGENT`                 |
| `summary`            | Required; trimmed length 5–150 characters                      |
| `description`        | Required; trimmed length 10–5000 characters                    |

The backend shall generate:

* `id`
* `ticketNumber`
* `ticketDate`
* Requester ownership
* Initial `currentStatus` of `NEW`
* `createdAt`
* `updatedAt`

Successful response:

```http
201 Created
```

```json
{
  "ticket": {
    "id": 101,
    "ticketNumber": "TKT-2026-00001",
    "ticketDate": "2026-09-03T14:30:00.000Z",
    "requester": {
      "id": 1,
      "name": "Development Requester 1"
    },
    "category": {
      "id": 1,
      "name": "Hardware"
    },
    "relatedSystem": {
      "id": 2,
      "name": "Learning Management System"
    },
    "requestedPriority": "MEDIUM",
    "currentStatus": "NEW",
    "summary": "Laptop battery drains quickly",
    "description": "The battery decreases from full to empty in approximately one hour.",
    "createdAt": "2026-09-03T14:30:00.000Z",
    "updatedAt": "2026-09-03T14:30:00.000Z"
  },
  "replayed": false
}
```

#### Ticket Number Generation

* The backend shall generate `TKT-YYYY-NNNNN`.
* `YYYY` uses the backend Ticket creation year.
* The sequence resets for each year.
* Generation and Ticket insertion shall occur in one database transaction.
* Concurrent creation requests must not receive the same Ticket Number.
* The client must never predict or provide a Ticket Number.

#### Idempotency

The combination of Requester and `clientSubmissionId` shall be unique.

* The first valid request creates the Ticket and returns `201 Created`.
* Repeating the same Requester, `clientSubmissionId`, and payload returns the existing Ticket with `200 OK`.
* Reusing the same Requester and `clientSubmissionId` with a different payload returns `409 Conflict`.
* A recoverable response failure after database commit must not cause a duplicate Ticket when the client retries.

Idempotency-conflict response:

```http
409 Conflict
```

```json
{
  "error": {
    "code": "IDEMPOTENCY_CONFLICT",
    "message": "This submission identifier has already been used with different Ticket data."
  }
}
```

Possible responses:

| Status | Error Code             | Condition                                       |
| -----: | ---------------------- | ----------------------------------------------- |
|  `201` | —                      | Ticket created                                  |
|  `200` | —                      | Existing Ticket returned for an identical retry |
|  `400` | `REQUESTER_REQUIRED`   | Requester header missing or malformed           |
|  `400` | `INVALID_REQUESTER`    | Requester unknown or inactive                   |
|  `400` | `VALIDATION_ERROR`     | Request body invalid                            |
|  `409` | `IDEMPOTENCY_CONFLICT` | Submission UUID reused with different data      |
|  `500` | `INTERNAL_ERROR`       | Unexpected failure                              |
|  `503` | `SERVICE_UNAVAILABLE`  | Database unavailable                            |

### 6.2 List Selected Requester’s Tickets

```http
GET /api/tickets
X-Development-Requester-Id: 1
```

Supported query parameters:

| Parameter           | Type             | Default     | Rules                                                                      |
| ------------------- | ---------------- | ----------- | -------------------------------------------------------------------------- |
| `search`            | String           | Empty       | Case-insensitive partial match against Ticket Number or Summary            |
| `categoryId`        | Positive integer | Empty       | Exact Category filter                                                      |
| `relatedSystemId`   | Positive integer | Empty       | Exact Related System filter                                                |
| `requestedPriority` | Enum             | Empty       | `LOW`, `MEDIUM`, `HIGH`, or `URGENT`                                       |
|`currentStatus`            | Enum             | Empty       | Approved Ticket status value                                               |
| `sortBy` | Enum | `updatedAt` | `ticketNumber`, `ticketDate`, `updatedAt`, `summary`, or `requestedPriority` |
| `sortOrder`         | Enum             | `desc`      | `asc` or `desc`                                                            |
| `page`              | Positive integer | `1`         | Page numbering begins at 1                                                 |
| `pageSize`          | Integer          | `10`        | Permitted values: `10`, `25`, or `50`                                      |

Approved Ticket status query values are:

* `NEW`
* `ASSIGNED`
* `IN_PROGRESS`
* `PENDING_REQUESTER`
* `RESOLVED`
* `CLOSED`
* `CANCELLED`

Lab 2 creates Tickets only with `NEW`. Later status changes remain outside the Lab 2 scope.

Example request:

```http

X-Development-Requester-Id: 1
```

Successful response:

```http
200 OK
```

```json
{
  "items": [
    {
      "id": 101,
      "ticketNumber": "TKT-2026-00001",
      "ticketDate": "2026-09-03T14:30:00.000Z",
      "category": {
        "id": 1,
        "name": "Hardware"
      },
      "relatedSystem": {
        "id": 2,
        "name": "Learning Management System"
      },
      "requestedPriority": "MEDIUM",
      "currentStatus": "NEW",
      "summary": "Laptop battery drains quickly",
      "createdAt": "2026-09-03T14:30:00.000Z",
      "updatedAt": "2026-09-03T14:30:00.000Z"
    }
  ],
  "pagination": {
    "page": 1,
    "pageSize": 10,
    "totalItems": 1,
    "totalPages": 1,
    "hasPreviousPage": false,
    "hasNextPage": false
  }
}
```

#### List Rules

* Only Tickets belonging to the selected Requester shall be returned.
* Search shall trim surrounding whitespace.
* Empty search and filter parameters shall be treated as absent.
* All filtering and ownership conditions shall be applied before pagination.
* Default ordering is `updatedAt DESC`, followed by `id DESC`.
* The secondary `id` sort shall always be applied for stable pagination.
* An empty result returns `200 OK` with an empty `items` array.
* A page beyond the available range returns `200 OK` with an empty `items` array and valid pagination metadata.
* Invalid enum values, non-integer identifiers, invalid pages, or unsupported page sizes return `400 Bad Request`.
* Sorting shall use a server-side whitelist. Raw client values must not be inserted into SQL.

Invalid-query response:

```http
400 Bad Request
```

```json
{
  "error": {
    "code": "INVALID_QUERY",
    "message": "One or more query parameters are invalid.",
    "fields": {
      "pageSize": "Page size must be 10, 25, or 50."
    }
  }
}
```

Possible responses:

| Status | Error Code            | Condition                                     |
| -----: | --------------------- | --------------------------------------------- |
|  `200` | —                     | Ticket page returned, including an empty page |
|  `400` | `REQUESTER_REQUIRED`  | Requester header missing or malformed         |

## 7. Attachment Endpoints

### 7.1 Attachment Metadata Shape

Attachment JSON responses shall use:

```json
{
    "id": 501,
    "ticketId": 101,
    "originalFilename": "battery-report.pdf",
    "mimeType": "application/pdf",
    "sizeBytes": 245760,
    "uploadedByRequesterId": 1,
    "isRemoved": false,
    "createdAt": "2026-09-03T14:35:00.000Z",
    "removedAt": null,
    "removedByRequesterId": null,
    "removalReason": null
}
```

Rules:

* `isRemoved` is `false` for active attachments and `true` for removed attachments.
* `originalFilename` is retained only for display and download naming.
* SeaweedFS object identifiers, bucket names, internal URLs, and storage paths must not appear in API responses.
* Removed attachment metadata remains retrievable by the owning Requester.
* Removed attachment content is not retrievable.

### 7.2 Upload Attachment

```http
POST /api/tickets/:ticketId/attachments
X-Development-Requester-Id: 1
Content-Type: multipart/form-data
```

Path parameter:

| Parameter  | Type             | Rules                                                  |
| ---------- | ---------------- | ------------------------------------------------------ |
| `ticketId` | Positive integer | Must identify a Ticket owned by the selected Requester |

Multipart field:

| Field  | Type        | Required | Rules                                                      |
| ------ | ----------- | -------: | ---------------------------------------------------------- |
| `file` | Binary file |      Yes | One JPG, JPEG, PNG, WEBP, or PDF file no larger than 5 MB |

Allowed MIME types:

* `image/jpeg`
* `image/png`
* `image/webp`
* `application/pdf`

Upload validation shall not rely only on the filename extension. The backend shall validate the declared MIME type and inspect the file signature where practical.

Successful response:

```http
201 Created
```

```json
{
    "id": 501,
    "ticketId": 101,
    "originalFilename": "battery-report.pdf",
    "mimeType": "application/pdf",
    "sizeBytes": 245760,
    "uploadedByRequesterId": 1,
    "isRemoved": false,
    "createdAt": "2026-09-03T14:35:00.000Z",
    "removedAt": null,
    "removedByRequesterId": null,
    "removalReason": null
}
```

#### Upload Rules

* The Ticket must belong to the selected Requester.
* A Ticket may have no more than five active Attachments.
* Removed Attachments do not count toward the active limit.
* The original filename shall be sanitized for response headers but shall not be used as a storage path.
* The server shall generate the SeaweedFS storage identifier.
* The file shall not be written permanently to the application source directory.
* The backend shall reject unexpected multipart fields and missing files.
* One request uploads one file so that individual failures can be reported clearly.

#### Upload Compensation

The upload sequence shall be:

1. Validate Requester context and Ticket ownership.
2. Validate the active attachment count.
3. Validate the file type and size.
4. Upload the binary to SeaweedFS using a generated storage identifier.
5. Create the Attachment metadata row in PostgreSQL.
6. Return the created metadata.

If SeaweedFS upload fails, no metadata row shall be created.

If SeaweedFS succeeds but PostgreSQL metadata creation fails, the backend shall attempt to delete the newly stored object as compensation and return a safe error.

Possible responses:

| Status | Error Code                    | Condition                             |
| -----: | ----------------------------- | ------------------------------------- |
|  `201` | —                             | Attachment uploaded                   |
|  `400` | `REQUESTER_REQUIRED`          | Requester header missing or malformed |
|  `400` | `INVALID_REQUESTER`           | Requester unknown or inactive         |
|  `400` | `INVALID_TICKET_ID`           | Ticket identifier malformed           |
|  `400` | `FILE_REQUIRED`               | Multipart file missing                |
|  `404` | `TICKET_NOT_FOUND`            | Ticket missing or not owned           |
|  `409` | `ATTACHMENT_LIMIT_REACHED`    | Five active Attachments already exist |
|  `413` | `ATTACHMENT_TOO_LARGE`        | File exceeds 5 MB                    |
|  `415` | `UNSUPPORTED_ATTACHMENT_TYPE` | File type not allowed                 |
|  `500` | `INTERNAL_ERROR`              | Unexpected failure                    |
|  `503` | `STORAGE_UNAVAILABLE`         | SeaweedFS unavailable                 |
|  `503` | `SERVICE_UNAVAILABLE`         | Database unavailable                  |

### 7.5 Preview or Download Active Attachment Content

```http
GET /api/tickets/:ticketId/attachments/:attachmentId/content
X-Development-Requester-Id: 1
```

Optional query parameter:

| Parameter     | Values                 | Default      | Behavior                                 |
| ------------- | ---------------------- | ------------ | ---------------------------------------- |
| `disposition` | `inline`, `attachment` | `attachment` | Preview or download response disposition |

Successful response:

```http
200 OK
Content-Type: application/pdf
Content-Length: 245760
Content-Disposition: attachment; filename="battery-report.pdf"
X-Content-Type-Options: nosniff
```

The response body contains the binary file.

#### Content Rules

* Ownership and active status shall be confirmed before retrieving the binary.
* `inline` may be used only for approved image and PDF MIME types.
* `attachment` instructs the browser to download the file.
* The Content-Disposition filename shall be safely encoded and sanitized.
* Internal SeaweedFS identifiers shall not appear in headers.
* The server shall use the stored approved MIME type.
* `X-Content-Type-Options: nosniff` shall be included.

Removed owned attachment response:

```http
410 Gone
```

```json
{
  "error": {
    "code": "ATTACHMENT_REMOVED",
    "message": "This attachment is no longer available."
  }
}
```

Possible responses:

| Status | Error Code              | Condition                              |
| -----: | ----------------------- | -------------------------------------- |
|  `200` | —                       | Active binary returned                 |
|  `400` | `INVALID_DISPOSITION`   | Unsupported disposition value          |
|  `400` | `INVALID_TICKET_ID`     | Ticket identifier malformed            |
|  `400` | `INVALID_ATTACHMENT_ID` | Attachment identifier malformed        |
|  `404` | `ATTACHMENT_NOT_FOUND`  | Resource missing or not owned          |

### 7.6 Soft-Remove Attachment

```http
DELETE /api/tickets/:ticketId/attachments/:attachmentId
X-Development-Requester-Id: 1
Content-Type: application/json
```

Request body:

```json
{
  "removalReason": "Uploaded the wrong image."
}
```

Validation:

| Field    | Rules                                     |
| -------- | ----------------------------------------- |
| `removalReason` | Required; trimmed length 5–200 characters |

Successful response:

```http
200 OK
```

```json
{
    "id": 502,
    "ticketId": 101,
    "originalFilename": "old-photo.jpg",
    "mimeType": "image/jpeg",
    "sizeBytes": 102400,
    "uploadedByRequesterId": 1,
    "isRemoved": true,
    "createdAt": "2026-09-03T14:36:00.000Z",
    "removedAt": "2026-09-03T14:40:00.000Z",
    "removedByRequesterId": 1,
    "removalReason": "Uploaded the wrong image."
}
```

#### Removal Rules

* The Ticket must belong to the selected Requester.
* The Attachment must belong to the specified Ticket.
* Only an active Attachment may be removed.
* Removal is a soft removal of the PostgreSQL metadata.
* The backend shall set the removal timestamp and reason.
* The metadata row shall not be deleted.
* Removed content becomes unavailable immediately through the API.
* Repeating removal of an already removed owned Attachment returns `409 Conflict`.
* The active attachment count shall exclude the removed Attachment after success.

#### Binary Cleanup

After the database marks the Attachment as removed, the backend shall attempt to delete its SeaweedFS object.

If binary deletion fails:

* The Attachment remains marked as removed.
* The API must continue blocking preview and download.
* The failure shall be recorded in server logs without exposing internal details.
* Cleanup may be retried by a later maintenance process.

Possible responses:

| Status | Error Code                   | Condition                        |
| -----: | ---------------------------- | -------------------------------- |
|  `200` | —                            | Attachment soft-removed          |
|  `400` | `VALIDATION_ERROR`           | Removal reason invalid           |
|  `400` | `INVALID_TICKET_ID`          | Ticket identifier malformed      |
|  `400` | `INVALID_ATTACHMENT_ID`      | Attachment identifier malformed  |
|  `404` | `ATTACHMENT_NOT_FOUND`       | Resource missing or not owned    |
|  `409` | `ATTACHMENT_ALREADY_REMOVED` | Owned Attachment already removed |
|  `500` | `INTERNAL_ERROR`             | Unexpected failure               |
|  `503` | `SERVICE_UNAVAILABLE`        | Database unavailable             |


## 8. Ownership and Authorization Rules

Lab 2 does not implement real authentication or production role-based authorization. However, the backend must still enforce Requester ownership using the selected Development Requester context.

### 8.1 Ownership Matrix

| Capability               | Ownership Requirement                                            |
| ------------------------ | ---------------------------------------------------------------- |
| Create Ticket            | Ticket owner is taken from the active Requester header           |
| List Tickets             | Return only Tickets owned by the selected Requester              |
| Get Ticket Detail        | Ticket must belong to the selected Requester                     |
| Upload Attachment        | Parent Ticket must belong to the selected Requester              |
| List Attachment Metadata | Parent Ticket must belong to the selected Requester              |
| Get Attachment Metadata  | Attachment’s Ticket must belong to the selected Requester        |
| Preview or Download      | Active Attachment’s Ticket must belong to the selected Requester |
| Soft Remove              | Attachment’s Ticket must belong to the selected Requester        |

### 8.2 Ownership Query Requirement

Ownership checks shall occur in the backend query or transaction, not only in the client.

The backend must not:

* Retrieve an arbitrary resource and return it before ownership is checked.
* Trust `requesterId` supplied in a Ticket or Attachment body.
* Depend on hidden UI controls as an authorization mechanism.
* Return different messages for missing and non-owned resources.
* Include another Requester’s records in counts or pagination metadata.

### 8.3 Transition to Lab 3

`X-Development-Requester-Id` is temporary. Lab 3 may replace it with authenticated server-side identity.

Ticket and Attachment services should receive a resolved Requester identity from a shared request-context layer so the domain logic can later adopt real authentication without rewriting ownership rules.

## 9. Validation and Security Requirements

### 9.1 Input Validation

* Validate path, query, header, JSON, and multipart inputs at the API boundary.
* Use reusable validation schemas.
* Reject non-finite numbers, negative identifiers, invalid enums, and malformed UUIDs.
* Apply backend validation even when the client has already validated the input.
* Use Prisma parameterization and never construct SQL with untrusted string concatenation.
* Use an explicit whitelist for sortable fields and sort direction.
* Apply reasonable body and multipart limits before processing large payloads.

### 9.2 Output Safety

* Use explicit response DTOs.
* Do not serialize Prisma models directly.
* Do not return SeaweedFS storage identifiers or internal metadata.
* Do not return inactive Requester information from the selection endpoint.
* User-entered content shall be returned as plain data and rendered as text by the client.
* Responses must not include secrets or internal implementation details.

### 9.3 Attachment Safety

* Allow only the approved image and PDF types.
* Limit each file to 5 MB.
* Limit each Ticket to five active Attachments.
* Generate storage identifiers on the backend.
* Never use an uploaded filename as a storage path.
* Sanitize filenames used in `Content-Disposition`.
* Include `X-Content-Type-Options: nosniff` for binary responses.
* Block content access immediately after soft removal.
* Record storage failures only in protected server logs.

### 9.4 Logging

Server logs may include:

* Safe operation name
* HTTP method and route
* Status code
* Correlation or request identifier
* Non-sensitive resource identifier
* Internal exception details in protected development logs

Server logs and responses must not expose:

* Database credentials
* Environment-variable values
* Raw file contents
* Internal SeaweedFS credentials
* Requester-sensitive records unrelated to the request
