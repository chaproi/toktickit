## 1. Exact proposed replacement for D-12

The following block is the complete proposed replacement; it must not be labelled “Accepted” without review. Section3 is its concrete protocol, not an optional implementation sketch.

> **D-12 — Proposed amendment: explicit command coordination and authoritative READ COMMITTED mutation transactions.**
>
> Retain Ticket `expectedUpdatedAt`, Action `version`/`expectedVersion`, Action `expectedTicketUpdatedAt`, all existing role/ownership/confirmation/lifecycle/field guards, and database-millisecond strictly advancing Action/parent timestamps. Retain User-before-Ticket-before-Action ordering, atomic domain/history/receipt writes, safe DTOs/errors, and replay-before-stale/frozen precedence. Do not introduce a Ticket version, new client token, additional HTTP retry, or minimum completed-Action/follow-up/work-cycle requirement.
>
> Replace the designated Ticket/Action/User command transactions’ SERIALIZABLE isolation and database/schema-wide exclusive writer admission with READ COMMITTED transactions protected by the explicit coordination protocol in this proposal. Remove the all-selected-writers per-pool FIFO for those commands. Use transaction-attempt-owned PostgreSQL resource gates across processes, not an in-process mutex or per-Ticket gate alone. Normal commands acquire compatible shared maintenance admission; reseeding/maintenance acquires exclusive maintenance admission. Last-active-Administrator membership, normalized email identity, User eligibility/actor identity, Ticket numbering, parent Tickets and Actions have the separate gates specified below. Independent commands with disjoint required resources may overlap; same-actor commands deliberately remain serialized for receipt identity. No general SERIALIZABLE guarantee is claimed for arbitrary unguarded SQL or nonparticipating writers.
>
> Declare and acquire the complete applicable coordination footprint before the business BEGIN, in the fixed order maintenance → Administrator membership → normalized email keys → User IDs ascending → numbering years → Ticket IDs ascending → Action IDs ascending. A User-protected owner-set discovery may determine additional Ticket IDs before that Ticket phase; it is repeated authoritatively inside the transaction. Never acquire an earlier-ranked resource after a later one. Preliminary discovery is not authorization. After BEGIN, lock current User rows in ascending ID order, then relevant session rows, reference/numbering rows where applicable, Ticket rows ascending, and Action rows ascending. Recheck current authorization/session, eligibility, resource identity, tokens, status and operation guards under those protections. A changed preliminary owner/assignee dependency must fail safely under the existing operation-specific conflict precedence, never acquire a late User lock or cause an unconfirmed automatic retry.
>
> All writers capable of introducing a matching row into a guarded set must participate: the assignee User gate protects unfinished-assignment eligibility, the owner User gate protects nonterminal ownership, the Ticket gate protects child insertion/status predicates, the membership gate protects the active-Administrator count, the email gate protects an absent normalized email, and the year gate protects an absent numbering row. Missing receipts are protected by the existing actor User gate plus the unique `(actorId,clientMutationId)` constraint. Existing-row locks alone do not protect missing rows or sets. Missing target resources may be rejected; command code must not recreate or reuse a requested missing entity ID. Seed and external maintenance follow the exclusive/quiesced protocol, not an unguarded bypass.
>
> Within each mutation-command transaction, authenticate and reauthorize from current locked state before returning a mutation or replay result. Inspect the original receipt before stale/frozen/terminal and mutable assignee-plan checks; preserve canonical original input and PATCH omission/null semantics. D-13's separate read-only recovery retains its current authorized read semantics without new row/gate locks. Successful writes, complete snapshots, versions, server times and receipts commit together; any failure rolls back the entire attempt before retry or defensive recovery. A receipt replay, rejection or no-op introduces no domain/history/time/receipt change. Preserve existing endpoint-specific guard priority and safe status/code mappings.
>
> Preserve existing connect, pool-acquisition, effective `maxWait` and execution-time budgets, constructor/per-call overrides and seed-only execution override. Resource coordination replaces the former global admission within the same single startup allowance; it never restarts that allowance. Execution timeout remains separate. Hold owned coordination until the business transaction and entered callback drain, then unlock and physically release exactly once; expire safely, drain late results, and never run a business callback after startup expiry. Do not retain the old global FIFO as a hidden serialization point.
>
> Retry a complete command in a fresh transaction only on positively confirmed structured PostgreSQL SQLSTATE `40001`, at most three attempts total. Every retry reacquires the complete footprint and rereads authorization, eligibility, tokens and receipt. Ordinary gate waiting at READ COMMITTED does not manufacture `40001` or require a snapshot-refresh retry. Unknown/generic `P2034`, `P2028`, `40P01`, uniqueness, message-only and unexpected failures are not serialization retry evidence. Exhaustion remains safe `409 CONCURRENT_UPDATE`. Keep D-13’s positively identified receipt-constraint, rollback-first, one fresh authorized read-only recovery separate; it is not a fourth mutation attempt.
>
> Dashboard/list read-only REPEATABLE READ snapshots, ordinary read authorization/projections, receipt-recovery isolation, inherited unrelated SERIALIZABLE operations and their error/retry policy remain unchanged. Adoption requires the writer/invariant proof and tests below, a quiesced all-process protocol switch, and reviewed D-12/D-13/API/test traceability updates. This amendment does not establish latency, T-47, memory-growth bounds, production release approval or scenario/DoD completion.

## 3. Concrete coordination and physical locks

Use public PostgreSQL **session advisory locks on the same checkout** later handed to the official adapter. Track each acquired key and release it once, reverse order, only after transaction/callback draining. No private engine hook, client rotation, persistent lock-row table or per-request pool shutdown.

The proposed two-integer namespaces below are code protocol, not installed database objects. Validate IDs before casting. `schemaOid` is the verified live schema OID represented as signed32 bits; absent/replaced schemas fail closed. Schema DDL requires quiescence.

| Rank/key | Exact target/mode | Participants |
|---|---|---|
| M `(1001,schemaOid)` | Shared for normal participants; exclusive for seed/maintenance. Never upgrade S→X. | All User/Ticket/Action/registry/reference/numbering/domain-child writers. Compatible S/S does not serialize ordinary work. |
| A `(1002,schemaOid)` | Exclusive active-Administrator membership set. | Every Administrator User create/edit, even when input appears unchanged. Seed is excluded by M/X. Reset/password/Ticket/Action work does not take A. |
| E `(1003,emailHash)` | Exclusive normalized old/proposed email identities; signed hashes sorted and deduplicated. | User create/edit. Retain trim/lowercase and existing SHA-256 first signed32-bit hash; compare full case-insensitive email after locking. Collisions add serialization, never identity. |
| U `(1,userId)` | Exclusive actor, discovered current owner/assignee and proposed owner/assignee; IDs ascending. | Relevant domain commands, login/session creation, password change/reset and User edits. Same actor remains serialized across Tickets. |
| Y `(1004,UTCyear)` | Exclusive year namespace, even with no sequence row. | Requester Ticket creation; seed allocator under M/X. |
| T `(2,ticketId)` | Exclusive parent keys; IDs ascending. | Every Action/Ticket writer and existing communication/attachment writer; User edit's protected owned-Ticket set. |
| X `(3,actionId)` | Exclusive existing Action keys; IDs ascending. | Existing Action mutations and cancellation cascade after T. |

M/A are schema-specific. U/T/X and E/Y remain conservatively database-wide: equal IDs/hashes/years across schemas may contend. This is explicit coupling, not a tenant-independence guarantee. Different ranks cannot alias. Within a rank sort actual keys and deduplicate. Only compatible M/S is universal among ordinary commands.

**Footprint discovery is not authority.** Preliminary owner/assignee IDs only choose U keys. After U(target), a User editor may discover nonterminal-owned Ticket IDs for the sorted T phase: all ways of entering/leaving that ownership set require the same U. After T, cancellation can discover unfinished Action IDs for sorted X. Repeat the predicates authoritatively after BEGIN. Unexpected drift fails safely, not a late lower-ranked lock or an unconfirmed planning retry. PATCH keeps its post-receipt discovery conflict; Staff operations retain existing stale/owner/eligibility priority. Already-mine claim no-op remains valid because the actor is covered. An actual old email outside the declared E set cannot be changed by acquiring E late.

**Physical order after BEGIN:** existing User rows `FOR UPDATE`, ascending IDs → relevant AuthSession rows, UUID ascending → Category then RelatedSystem `FOR SHARE` where active references are needed → numbering row `FOR UPDATE`/upsert under Y → Ticket rows `FOR UPDATE`, IDs ascending → Action rows `FOR UPDATE`, IDs ascending. Build one ordered session set containing the request session ID and all current sessions to revoke; login insertion is excluded by the target U gate. Use `FOR SHARE` for a session only being checked and `FOR UPDATE` from first access for any session to delete/replace, including the caller's own session during password change. No SHARE→UPDATE upgrade is needed. Validate the own session before any domain result. Prelock affected sessions before Ticket locks, then delete only after existing guards pass. Concurrent logout can remove rows from that set but cannot add them. New IDs use database allocation, not requested missing IDs. Inserts reference already protected User/parent/reference rows. Historical identity-name projection may use ordinary safe reads, not new User locks after T/X.

**Current-owner coverage is mandatory even where owner eligibility is not.** Before a converted Ticket writer changes ownership or nonterminal membership, validate that a non-null current owner is included in the acquired U footprint. This applies to cancellation/closure as well as owner-required transitions. Preserve existing terminal/stale/transition precedence; uncovered discovery fails through the existing owner-eligibility/concurrency conflict mapping, with no new lock or automatic retry. A covered inactive historical owner does not become an eligibility requirement for cancellation, and null requires no owner key. Current status code only checks owner drift inside owner-required transitions; that cannot simply be copied as the complete RC set-protection argument.

Legacy Comments/Notes/attachments retain SERIALIZABLE U/T transaction gates inside the callback; these conflict with new session-level gates for the same keys. Their waited-gate40001 rule remains. Add M/S startup participation through the existing helper; do not move their storage I/O or existing domain waits out of the execution budget. Session-only logout/expiry/touch may remain outside U if it takes no subsequent User/domain lock and never recreates deleted sessions. Login/new-session and User/password changes cannot use that exemption.

## 5. Sequence, deadlocks, independent overlap

1. Preserve HTTP session/Origin/CSRF/shape gates. Capture internal auth context and canonical original request/PATCH presence. Hashing/discovery outside the transaction confer no authority.
2. At public adapter startup start the one effective maxWait clock. Checkout, acquire M/S, optional A/E, sorted U. Discover only additional User-protected owned Ticket IDs, acquire Y/T, then discover cascade X under T. Each query uses remaining startup time, not a fresh allowance.
3. Restore statement_timeout and BEGIN RC on that same connection. Lock/read User, own/revoked sessions, references/numbering, Tickets and Actions in section3 order. Prelock target sessions before Ticket locks for User eligibility changes; delete later only after guards pass. Validate current authorization/session and required resource access only. Defer mutable owner/assignee dependency-footprint drift checks until after the original receipt has been inspected.
4. Read original receipt before drift/stale/frozen/terminal. Replay/conflict writes nothing. Otherwise evaluate tokens, eligibility, owner, confirmation, child and field predicates in inherited endpoint order. Unplanned dependency fails safely, without late lower-ranked locks or invented retry.
5. Apply existing atomic writes, receipt last. Preserve D-20 reasons, complete snapshots/source links, Action versions and server times. RC projection reads are not a global analytics snapshot.
6. Await COMMIT/rollback and callback draining; preserve primary error if cleanup fails. Unlock reverse order, release once. Expired startup cannot later run a business callback; execution-expired work cannot lose ownership while undrained.
7. Only trusted structured40001 starts a complete fresh attempt, max3. Defensive receipt recovery remains one separate authorized read-only transaction.

Legacy SERIALIZABLE communication/attachment M/S is startup work; original U/T waits stay within execution timeout. Converted commands replace global startup waiting with resource-specific startup waiting, not a fresh execution allowance. Keep numerical connect/pool/maxWait/execution settings, constructor/per-call overrides and seed15s exception. Row/session waits after BEGIN remain execution work. Test the actual boundaries.

All processes use M→A→E→U→Y→T→X; physical User rows precede session and parent/child rows. A/E before U avoids opposite seed-email/User ordering. Sort dynamic sets under their owning barrier. No maintenance upgrade or late User acquisition. Session-only logout/touch has no later User dependency; bulk revocation sorts session rows. Inserts reference already protected rows. Unexpected deadlocks from missed writers/triggers/external SQL remain possible, fail safely and are not retryable.

Disjoint actor/assignee/owner and Ticket/Action resources share only compatible M/S, so both callbacks can enter before either commits. Remove both old global exclusive admission **and its all-writer FIFO** for RC mode. Explicit hotspots remain same actor, common worker/owner, same Ticket/email, Admin membership, same-year numbering and seed maintenance. None is secretly required by every Action command.

Hot-key waiters can still occupy checkouts. Existing expiry/draining bounds them, not read latency/fairness. No additional queue or larger pool/budget is proposed. Read-only RR snapshots remain outside coordination. Session-only touch/logout/expiry may remain terminal row writers; login/new session and User/password changes must participate. Future writers must join this inventory. Migrations/restore/operational SQL require quiescence; native race participants are explicitly noncooperating evidence, not a guarantee for arbitrary SQL.
