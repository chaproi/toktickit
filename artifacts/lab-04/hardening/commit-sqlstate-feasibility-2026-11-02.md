The full application model is copied; only its temporary generator output/driverAdapters preview setting changes. Byte-identical copies of eligibility-transaction.ts, prisma.ts and test-database.ts resolve the single temporary generated client. A correctly typed application TransactionClient callback invokes the real inherited lockCurrentActor, ORM Category reads/updates and RelatedSystem inserts. It checks PostgreSQL backend/transaction identity before and after ORM work and sees its own staged insert. This is neither a direct-pg-only transaction nor an independently committed ORM write. Synthetic actors have no HTTP sessions; full live-session/Action behavior is a subsequent integration requirement.

For each pair, two actual SERIALIZABLE transactions use different backends/transaction IDs and different owned actor/row targets. Both read the same two active Categories, update different Categories and stage distinct RelatedSystem rows. **Both finish their statements before either COMMIT.** The coordinator releases and awaits the winner, then releases the loser. Consequently a real SSI dependency cycle fails during COMMIT, after the losing callback has completed. There is no raised SQLSTATE trigger or fake error.

## Smallest production design and required decision

**Decision required before production implementation:** accept or decline a pinned **5.22 preview driver-adapter adoption plus a small maintained public adapter composition**. This is a dependency/client-generation/driver-lifecycle decision, not permission supplied by this feasibility batch. No database DDL migration or new retry-contract decision is inherently needed for this path. If preview/custom-adapter maintenance is unacceptable, retain the current write blocker and commission a separately bounded supported upstream/version evaluation; no other version has been tested here.

If accepted, the smallest design is:

1. Enable driverAdapters only in the application client generator and add the matching adapter dependency. Construct one lazy Prisma client with the official pg adapter in the existing client-construction seam. Preserve the isolation guard and explicit test/operational separation. Translate schema, timezone, connection URL and pool lifecycle deliberately: the proof's four-connection pool is **not** a proposed application setting, and native-engine versus pg defaults must not silently change effective pool policy or budgets.
2. Compose only the public transaction query/result interface. For an actual COMMIT failure whose trusted typed Postgres code is **40001**, propagate a sanitized application Error cause carrying that code. The proof retained the native Result in memory for provenance; production must not expose its message/detail/hint or publish raw causes. Leave other adapter results/classifications alone unless separately demonstrated. No client-wide last error, message heuristic, exception-to-40001 conversion or generic P2034 retry.
3. Retain the current executor's maximum three fresh SERIALIZABLE attempts and on-failure cleanup semantics, User-before-Ticket-before-Action gates and full callback rereads. Callback output is returned only after successful COMMIT. Keep defensive receipt recovery separate.

Preview lifecycle risk is concrete: the inspected 5.22 binder stores thrown JS errors by ID and its consumeError implementation does not clear the array slot. The short-lived proof releases its clients/process and measures no long-lived heap behavior; production adoption needs a lifecycle/memory assessment, not an invented assertion that this is a cost-free drop-in. Upgrading to address that behavior has **not** been evaluated or authorized. Cross-version guarantees, all dependency mappings and HTTP error/log redaction are also not established by these three pairs.

Before any production GREEN, preserve tests-only meaningful RED and require:

- Real coordinated authorized independent CREATE and EDIT callbacks through the proposed client, successful native-COMMIT40001 attribution to the same attempt, full failed-attempt rollback before the next attempt, and exactly one committed Action/history/receipt/parent advancement per successful command.
- One/two actual confirmed failures then success; three confirmed failures yield exactly three attempts and safe 409 CONCURRENT_UPDATE, no domain writes, no fourth attempt. Fresh transaction/backend evidence; live session/role/eligibility/optimistic-token reads every attempt. Revoke/change state only after rollback and prove the next attempt observes it.
- Preserve T-42 negative boundaries: bare/unknown P2034, deadlock 40P01, P2002/23505, message-only/ambiguous and unexpected errors do not receive serialization retries. Prove no stale per-client/connection error is attached to a different transaction. Retain T-51/T-52 receipt semantics.
- Verify actual business raw/ORM/lock paths under one generated client, compensation, safe dependency/unexpected-error mapping and redaction, read-only Dashboard/list transactions, startup/shutdown and explicitly preserved pool/transaction settings. Reuse existing suites rather than duplicating T-42 merely for filenames.

These requirements are a concrete next authorized RED/GREEN batch proposal, not tests executed here. No relaxed retry decision is proposed. The failed benchmark, Queue correction and unestablished read-latency components remain separate; no performance result is improved by this feasibility evidence.
