# Prisma 5.22 adapter adoption compatibility gate - 2026-11-02

**Disposition: stop before application RED/GREEN.** The authorized candidate's demonstrated COMMIT transport works, but the proposed long-lived singleton has a quantified upstream retention problem. Pinned 5.22 exposes no supported registry-clear operation; silently patching that private storage is excluded. Application production/schema/manifests/locks/retry behavior remain unchanged. No full server suite/build or T-47 workload ran, because there is no candidate GREEN to verify.

This is the compatibility stop condition expressly required before implementation, not a reversal of the prior transport proof or an unsupported claim that all possible 5.22 designs are impossible. A separately designed bounded **public client lifecycle** could be investigated, or a specifically selected supported version evaluated. Neither remedy was implemented or proven here; the existing singleton must not be silently replaced with per-attempt clients or an arbitrary rotation/version to manufacture adoption.

## Quantified retention: upstream, not diagnostic Scope arrays

The [5.22 upstream binder](https://github.com/prisma/prisma/blob/5.22.0/packages/driver-adapter-utils/src/binder.ts) registers an Error in an array slot. consumeError returns the entry without removing it; subsequent registration scans for an unused slot. The [public interface](https://github.com/prisma/prisma/blob/5.22.0/packages/driver-adapter-utils/src/types.ts#L180) offers consumption, not clearing/disposal. The installed application library.js was inspected and contains the same non-deleting consume/register implementation; it was not accessed or patched at runtime. The existing singleton strongly retains its adapter registry while the client remains reachable.

The finite component assessment imports the **public** bindAdapter and exercises its returned public errorRegistry interface. No private array/property or generated engine is patched. A diagnostic DriverAdapter deliberately throws labelled synthetic JS exceptions; **no synthetic PostgreSQL/40001 or HTTP outcome is claimed**. Every result is consumed immediately. Only numeric IDs/counters and two numeric summaries survive; there is no diagnostic Error array, no earlier feasibility Scope array and no global last-error cache.

Each retrieved cause's serial identity matched its original error ID. The exact observed growth is one retained upstream record per bridge exception over this bounded sample. Source explains continued retention for the live registry; this is not an extrapolated heap-byte measurement. Sanitizing causes reduces private-content risk and payload size but does not remove the registry slot. No production exception rate, heap capacity, GC reclamation schedule or memory-safety guarantee was measured. The short-lived prior proof still establishes transport; it never established bounded long-lived retention.

**Blocking implication for the demonstrated singleton design:** retryable commit exceptions would continue accumulating upstream records. There is no supported clear API in the pinned registry. Directly editing engine/errorRegistry internals or pretending $disconnect clears this live object's registry is not an acceptable correction. A safely bounded adoption needs a reviewed lifetime remedy or a version where cleanup is supported/proven. The current prompt explicitly requires reporting such a blocker before proceeding; no production candidate is committed here.
